## 1. ハードウェア確認結果

### 1.1 MCXA153（MCU）

| 項目 | 値 | 根拠 |
|---|---|---|
| コア | Cortex-M33、**FPU なし、DSP 拡張なし、MPU なし** | DEV `MCXA/MCXA153/MCXA153_COMMON.h` L181–185: `__MPU_PRESENT 0`, `__FPU_PRESENT 0`, `__DSP_PRESENT 0` |
| 最大クロック | **96 MHz**（FRO_HF） | EX `_boards/frdmmcxa153/clock_config.h` L150 `BOARD_BOOTCLOCKFRO96M_CORE_CLOCK 96000000U`。`clock_config.c` L55 で既定は `BOARD_BootClockFRO96M()`。ZEP `frdm_mcxa153.dts` の `clock-frequency = <96000000>` |
| Flash | **128 KB**（0x0000_0000–0x0001_FFFF） | DEV `gcc/MCXA153_flash.ld` L37–38（`m_interrupts` 0x200 + `m_text` 0x1FE00）。ZEP のボード説明にも「128KB dual-bank」 |
| SRAM | **合計 32 KB** = SRAM 24 KB（0x2000_0000, `m_data` 0x6000）+ SRAMX 8 KB（0x0400_0000, `m_sramx0` 0x2000） | DEV `gcc/MCXA153_flash.ld` L39–40。ZEP のボード説明にも「32 KB RAM」。SDK 標準のリンカスクリプトは SRAMX を**定義するだけで使っていない** |
| SDK 標準のスタック／ヒープ | スタック 2 KB、ヒープ 1 KB | 同じリンカスクリプトの L31–32 |
| eDMA | 1 インスタンス、**4 チャネル** | DEV `MCXA153_features.h` L275 `FSL_FEATURE_EDMA_MODULE_CHANNEL (4)` |
| LPSPI | 2 インスタンス（LPSPI0/1）、FIFO 4 ワード | 同 L65, L482 |
| FlexIO／LCDIC | **どちらもない**（`FSL_FEATURE_SOC_*_COUNT` に存在しない） | 同 L31–91 |
| LPSPI の eDMA 転送 | SDK にサンプルがある（`kDma0RequestLPSPI0Tx/Rx`） | EX `_boards/frdmmcxa153/driver_examples/lpspi/edma_b2b_transfer/master/app.h` |

**設計への影響**
- FPU がないので、float と double はすべてソフトウェアでエミュレーションされ、遅い。
  そのため、実行時の描画パスでは浮動小数点を**使わない**。
  使うのは、ホスト側のツールでテーブルやフォントデータを生成するときと、デバッグ用の printf だけにする。
- FlexIO も LCDIC もないため、8080 パラレル接続はハードウェアで支援されない。
  LCD は **LPSPI（4 線式 SPI）＋ eDMA** で駆動する（1.3 を参照）。

### 1.3 LCD-PAR-S035 と MCXA153 の接続

| 項目 | 確認結果 | 根拠 |
|---|---|---|
| LCD コントローラ | ST7796S。SDK に専用のプリセットがある | CMP `display/st7796s/fsl_st7796s.h` L44 `kST7796S_DriverPresetLCDPARS035`。向きの enum（`kST7796S_Orientation0/90/180/270`）、RGB565 形式、INVON もある |
| モジュールのインターフェース | SPI、または 8/16 ビットのパラレル（8080/6800） | ZEP `boards/shields/lcd_par_s035/doc/index.rst` |
| SPI 用の 12 ピン PMOD のピン配置 | 1,2 = VCC、3,4 = GND、**5 = WR（SPI の SCK）**、6 = タッチ SCL、**7 = D/C**、8 = タッチ SDA、**9 = MOSI**、**10 = LCD/タッチのリセット**、**11 = CS**、12 = タッチ INT | ZEP `dts/bindings/gpio/nxp,lcd-pmod.yaml` |
| SPI 時のパネル設定の実績値 | 4 線式 SPI、MADCTL=0x28（横向き 480x320）、色反転（INVON）が必要 | ZEP `boards/shields/lcd_par_s035/lcd_par_s035_spi.overlay` |
| 書き込みの速度 | ST7796S の書き込みサイクルは最小 66 ns（Zephyr のコメント） | 同じ overlay のコメント。SPI のクロック仕様値はデータシートで要確認 |
| **FRDM-MCXA153 側のコネクタ** | ボードの説明には「**Arduino Header, mikroBUS**」とだけある。**PMOD とパラレル LCD コネクタは記載がない** | ZEP `boards/nxp/frdm_mcxa153/doc/index.rst` L22。`frdm_mcxa153.dts` にも `nxp_lcd_pmod_connector` の定義はない（FRDM-RW612 などにはある） |
| SDK の既存サンプル | FRDM-MCXA153 向けの LCD／ST7796S サンプルは**ない**。ST7796S ドライバは `fsl_dbi` の抽象化に依存しているが、**LPSPI 用の DBI アダプタは SDK にない**（あるのは FlexIO、LCDIC、LPC SPI、LCDIF、DCIF 用だけ） | EX を `st7796|s035` で全検索して FRDM-MCXA153 の該当なし。CMP `video/display/dbi/` |

**結論（案）**: MCXA153 の LPSPI と LCD-PAR-S035 の PMOD（SPI）を**ジャンパ線で配線**する。

配線案 A（Arduino ヘッダの LPSPI1 を使う。ピンの根拠は ZEP `frdm_mcxa153.dts` の arduino_header と `frdm_mcxa153-pinctrl.dtsi` の pinmux_lpspi1）

| LCD PMOD | 信号 | FRDM-MCXA153 | MCU ピン |
|---|---|---|---|
| 5  | SCK (WR) | Arduino D13 | P2_12 (LPSPI1_SCK) |
| 9  | MOSI     | Arduino D11 | P2_13 (LPSPI1_SDO) |
| 11 | CS       | Arduino D10 | P2_6 (LPSPI1_PCS1) |
| 7  | D/C      | Arduino D2  | P2_4 (GPIO) ※案 |
| 10 | RESET    | Arduino D4  | P2_5 (GPIO) ※案 |
| 1/2, 3/4 | 3V3, GND | Arduino の電源ピン | — |

- D5/D6/D3（P3_12/P3_13/P3_0）は RGB LED なので使わない（EX `board.h` L40–58）。
- 配線案 B: mikroBUS の LPSPI0（P1_0=MOSI、P1_1=SCK、P1_3=CS）を使う。どちらを使うかは下の「要確認」で決めたい。
- MISO はつながない（書き込みのみ）。タッチ（GT911）は今回は使わない。
- PMOD に TE 信号がないため、垂直同期に合わせた書き込みはできない。ダーティ矩形を小さく保つことでティアリングを目立たなくする。

## 3. RAM の予算表

方針: ヒープは 0（malloc を使わない）。静的に確保する。自前のリンカスクリプトで SRAMX も使う。

### タイルのサイズ

- タイル（帯）は **160 × 16 px**（RGB565 で 5,120 B）。これを DMA 用に 2 面持つ（ダブルバッファ）。
- 転送時間: 5,120 B は SCK 24 MHz で約 1.7 ms、15 MHz で約 2.7 ms。
- 描画時間の見積もり: 2,560 px × 約 40〜60 cycle/px ÷ 96 MHz ≈ 1.1〜1.6 ms。転送とほぼ釣り合うので、ダブルバッファにする意味がある。
- ダーティ矩形はこのタイルに分割して処理する（幅 160 を超える矩形は横方向にも分割する）。

### SRAM（24,576 B, 0x2000_0000）

| 用途 | サイズ (B) | 備考 |
|---|---:|---|
| DMA タイルバッファ ×2 | 10,240 | 160×16×2 B ×2 面。DMA が確実に読める領域に置く |
| リニア光のラインバッファ | 1,024 | 160 px × RGB 各 16 ビット（960 B）。1 行分のブレンドをガンマ補正後の線形値で行う |
| カバレッジ累積バッファ | 1,024 | 161 × int32（644 B）＋ 1 行分のマスク 160 B |
| エッジバッファ | 4,096 | 256 本 × 16 B。図形ごと、タイルごとにクリップしてから格納する |
| アプリの状態 | 1,024 | 履歴 240 × int16 = 480 B、アニメーション状態、ダーティリスト（最大 16 矩形）、統計 |
| SDK ドライバ | 1,024 | eDMA ハンドルと TCD（32 B 境界に配置）、LPSPI、I3C、デバッグコンソール |
| その他の .data/.bss | 512 | |
| **合計** | **18,944** | **余裕 5,632 B**（トリプルバッファや幅の広いタイルに回す余地） |

### SRAMX（8,192 B, 0x0400_0000）

| 用途 | サイズ (B) | 備考 |
|---|---:|---|
| メインスタック | 4,096 | CPU だけがアクセスするので SRAMX で問題ない。フェーズ 7 でスタックの塗りつぶしパターンから最大使用量を測って詰める |
| 予備 | 4,096 | エッジバッファを移す、あるいは Q6 で DMA 可能と分かればタイルを 3 面にする |

### Flash（128 KB）の見積もり

| 用途 | 見積もり |
|---|---:|
| SDK ドライバ（clock、port、gpio、lpspi、edma、i3c、lpuart）＋スタートアップ | 約 20 KB |
| 描画エンジン | 約 12 KB |
| ガンマ LUT（sRGB→線形 256×u16 = 512 B、線形→sRGB 4096×u8 = 4 KB）、sin LUT（1 KB） | 約 6 KB |
| ベクターフォント（14 グリフ × 約 40 点） | 約 2 KB |
| アプリ | 約 6 KB |
| **合計** | **約 46 KB（余裕は十分）** |

## 4. 描画アーキテクチャ

```
センサー(250ms) ─▶ フィルタ ─▶ 目標値 ─▶ バネ(臨界減衰, Q16) ─▶ 表示値
                                                         │
                                シーン(ゲージ/数字/スパークライン/最高最低)
                                                         │ 前フレームとの差分
                                                    ダーティ矩形リスト
                                                         │ タイルに分割
             ┌───────── タイル k: 背景→トラック→値の円弧→グロー→文字 を 1 行ずつ合成 ─────────┐
             │   (線形光 16bit でブレンド) → ガンマ変換 + 4x4 Bayer ディザ → RGB565            │
             └──▶ タイルバッファ A/B ──(CASET/RASET → RAMWR, LPSPI 16bit フレーム, eDMA)──▶ ST7796S GRAM
```

- **フレームバッファを持たないので、読み戻しもしない。** タイルごとに、そのタイルに重なるレイヤーを全部合成し直す。
  背景のグラデーションもその場で計算する。
- **ラスタライザ**: パスは直線と 2 次・3 次ベジェ。ベジェは適応分割で直線に平坦化し、24.8 固定小数点のエッジにする。
  カバレッジは FreeType の smooth ラスタライザと同じ方式（セルごとに cover と area を持つ解析的な面積カバレッジ）で計算する。
  非ゼロ・ワインディング規則は、累積した値の絶対値を 1 で飽和させて実現する。
  処理は 1 行単位で、図形ごとにエッジを y でソートし、アクティブエッジをたどる。
- **ストローク**: 直線近似したポリラインを左右にオフセットし、丸いキャップと丸い結合を付けて閉じた輪郭にする。
  円弧のストロークは、同心の 2 つの円弧と両端の半円に分けて直接生成する（精度が高く、速い）。
- **ペイント**: 単色、線形グラデーション、円形グラデーション。色の停止点は最大 6 個で、線形光の値で補間する。
  ゲージの値側は角度方向のグラデーション（スイープ）にする。
  青 → シアン → 緑 → 琥珀 → 赤の停止点を、温度の範囲に対応させる。
- **グロー**: ぼかし用のバッファは RAM が足りないので作らない。
  円弧の先端からの距離 d を使い、`alpha = LUT(d / r)`（ガウス関数に近い減衰）で解析的に描く。
  同じように、円弧の中心線からの距離でうっすらとした外側のグローも付けられる。
- **ガンマ**: 入力色（sRGB 8 ビット）は LUT で線形 16 ビットに変換してからブレンドする。出力時に 4096 段の LUT で sRGB に戻す。
- **ディザ**: RGB565 に量子化する直前に、4×4 Bayer 行列で閾値をずらす（R/B は 3 ビット分、G は 2 ビット分）。
- **固定小数点**: 座標は 24.8、色は Q0.16、角度は 16 ビットで 1 回転（0x10000）、アニメーションは Q16.16。
  三角関数は 1024 点の sin LUT と線形補間で求める。
- **LPSPI の 16 ビットフレーム**: RGB565 を上位バイトから送るので、バイトスワップは不要のはず（フェーズ 2 で確認する）。

### ベクター数字フォント
- グリフは `0-9 . - ° C` の 14 個。閉じた輪郭（2 次ベジェ主体）を em = 1000 の int16 座標で Flash に置く。
- 細身のデザインは、ホスト側のツール（Python）で「骨格の中心線 + 線幅」から輪郭をオフセット生成し、C の配列として出力する。
  こうすると、ウェイトを調整してから再生成するのが簡単になる。実行時に使うのは輪郭データだけ。
- 数字は**等幅**（tabular figures）にする。値がアニメーションしても桁の位置が揺れないようにするため。
- 小数部分は 0.6 倍の大きさ、不透明度 70 % で描く。

## 6. フェーズと完了条件

## 7. 主なリスクと対策

| リスク | 対策 |
|---|---|
| SPI の帯域（全画面 307,200 B → 24 MHz で約 102 ms） | 全画面を描くのは起動時だけにする。アニメーション中はダーティ矩形を小さく保つ（数字の領域は約 220×100 px → 約 15 ms） |
| FPU がない | 実行時は固定小数点だけにし、LUT を使う。フェーズ 4 のテストで精度を担保する |
| RAM 不足 | ヒープは 0、スタックは SRAMX に置く。エッジはタイル単位でクリップして保持する |
| TE 信号がない | ダーティ矩形を小さくし、上から下に書く順序を守る |
| 配線のノイズ（ジャンパ線で 24 MHz 以上） | 線を短くし、GND を太く取る。15 MHz でも成り立つ設計にしておく |
